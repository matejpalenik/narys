# Human control plane for software factories

## 1. Summary

Test one decision first. Can a maintainer reviewing an agent-written pull request tell whether it preserves an architectural decision, explain the consequence of a change, and identify what evidence is missing? Use an existing GitHub workflow and a small, maintainer-confirmed architecture view. Compare the experience with GitHub plus the team's existing artifacts, then compare the canvas with the same evidence in a linear view.

Several products already support architecture diffs, intent traceability, agent orchestration, or evidence-backed review. Some combine these capabilities. The opportunity is a hypothesis about adoption cost and decision quality for small teams with existing code. A team may be able to review a consequential change with evidence it already owns, without migrating its design process or changing coding agents. The strongest counterexample is a team that can do this as well with an existing tool or a short PR template. [S08](#s08) [S09](#s09) [S10](#s10) [S11](#s11)

## 2. Research question and scope

Which recurring decision becomes harder as developers delegate code, and what is the smallest product experiment that can establish whether the proposed engineering model helps?

- **Candidate user.** A hands-on maintainer or tech lead in a small GitHub-based team who regularly reviews changes to code they own, including changes generated by agents. The hypothesized demand is highest where a boundary matters, an intent record exists or can be confirmed quickly, and the reviewer needs more context than a file diff supplies. A solo developer returning to a system after time away is a secondary candidate. Neither segment is validated.
- **Decision.** Choose what to prove first among architecture exploration, evidence-backed PR review, design and approval before implementation, or the complete delegation loop.
- **Evidence.** Public standards descriptions, original studies, first-party product documentation, and upstream repositories. Commercial capabilities are documented claims. This research includes no interviews, comparative task runs, private-repository pilots, or provider API execution.

### 4.1 Challenge the premises

**Technical debt costs.** A field study of 4,867 developers estimated about 26% more completed tasks among users of a coding assistant. METR's early-2025 randomized study of 16 experienced maintainers on 246 tasks found that AI access increased completion time by 19%. METR's later study suggested better performance with newer tools, with participation and measurement problems that limit the estimate. Demirer, Musolff and Yang's matched analysis found larger gains in commits than in shipped releases, consistent with downstream bottlenecks. It did not isolate review as the cause. These studies do not establish that maintaining or refactoring a system is cheaper over its life. An agent may reduce the effort to generate a refactor while expanding the review and integration work needed to trust it. [S05](#s05)

**Cognitive and intent debt.** Storey proposes cognitive debt as erosion of understanding and intent debt as missing or disconnected externalized goals, constraints, and rationale. Her Cognitive Tours demo links needs, decisions, code, tests, and open questions. The author reports dogfooding and expressly leaves efficacy to future evaluation. An Anthropic randomized study found weaker comprehension or skill formation in a bounded Python library learning task with AI access. It does not establish the effect on long-term team understanding. Preserve the human task of judging which relationships matter. A plausible generated explanation can make a reviewer feel oriented without improving their judgment. [S06](#s06) [S07](#s07)

**Control, coordination, and assurance.** An owner exercises control by being able to make and revise a meaningful decision. A green check can support that decision only within its coverage and at its tested revision. Existing orchestration products can already distribute work and collect results. The first-principles question is whether a human can resolve the consequential uncertainty faster or more accurately with the intervening model. [S11](#s11) [S12](#s12) [S14](#s14)

## 5. Alternatives and trade-offs

| Approach | What it tests | Cost or limiting condition | Evidence |
|---|---|---|---|
| Architecture exploration or guided tour | Whether people can explain a component or predict the effect of a change | Can test mental models with little integration. Whole-repository mapping can consume more effort than the initial decision warrants. Strong existing diagramming substitutes. | [S07](#s07) [S08](#s08) |
| **Review one change against one architectural decision** | Whether a maintainer makes a better-supported decision on an existing PR | Requires credible code anchors, a decision the owner can confirm, and attention to the compared and checked revisions. Current tools may be sufficient. | [S09](#s09) [S10](#s10) [S14](#s14) |
| Design and approve before coding | Whether a maintainer can set a clearer boundary and prevent a costly mistake before code exists | Valuable if reviewers report that post hoc findings come too late. Requires authoring, revisions, approval semantics and user attention earlier in the workflow. | [S10](#s10) [S11](#s11) [S12](#s12) |
| Full design-to-delegation loop | Whether the platform can direct implementation and close the loop against approved intent | Bundles discovery, review, execution, provider permissions, failures, and reconciliation. Early results are harder to attribute to the shared model. | [S11](#s11) [S12](#s12) [S15](#s15) [S16](#s16) |

### Technical options to revisit after discovery

- **GitHub and evidence.** Start evaluation with an existing public PR or a consented fixture. GitHub can supply changed files, check details and deployment statuses when available. Read data on demand. Use the exact repository, candidate, comparison basis, observed revision and check issuer. A `pull_request` workflow commonly checks a test merge commit. A new candidate needs a fresh assessment. Private-repository access and unattended events introduce permission and reconciliation work. [S14](#s14)
- **Architecture model and persistence.** Compare a small versioned repository document containing confirmed relationships with a single application database. Git offers portability and artifact review. SQLite is a candidate for local or single-host persistence, subject to its concurrency and deployment constraints. A server database becomes relevant if approved use needs shared writes across hosts. Keep source-derived observations and confirmed intent distinguishable in every view. An existing format such as CALM merits a compatibility check before a custom schema. [S03](#s03) [S18](#s18)
- **Interface and updates.** Next.js and React are viable candidates. React Flow is one graph renderer to evaluate, including keyboard and accessible operation on the real task. Compare a canvas against an equally capable linear view before choosing interaction primitives. On-demand refresh is enough for a historical PR evaluation. If live updates become valuable, compare polling and server-sent events before adding durable event infrastructure. Treat shadcn/ui and Storybook as the user's preferred component and verification tooling for an approved React stack. [S18](#s18)
- **Managed agents.** OpenAI's Agents API is a public beta offering managed Codex sessions, hosted or self-hosted execution, and streaming or webhooks. Its data residency, retention, and best-effort session budget need review against any eventual policy. GitHub's Copilot task API is a preview with user-to-server authentication for task management. Claude Managed Agents is another beta option, and the Codex SDK exposes local execution. Compare one provider only when dispatch becomes a required outcome. The application would still own approval, Git permissions and the mapping from provider activity to reviewed evidence. [S15](#s15) [S16](#s16)
- **Engineering standards.** At architecture approval, identify the real boundaries before choosing domain patterns. GitHub observes PR and integration state. A maintainer owns confirmed intent. A verification provider produces observations. Stable contracts between these responsibilities are likely useful. DDD, inward dependencies and logical CQRS can be adopted proportionately without separate data stores or services. See the [installed standards skill](../../.agents/skills/engineering-standards/SKILL.md).

## 6. Conclusions and recommendations

**Run a review experiment first.** Give a maintainer one existing PR, one architectural decision, and a small map of affected components with links to the underlying source and check results. Ask the maintainer to decide whether to approve, request a change, or seek more evidence. Leave the real approval and merge in the existing workflow.

Illustrative fixture. An ADR requires the Orders domain to depend on a payment interface. An agent adds a direct import of the payment provider, and the visible green test result is from the previous head. The reviewer should be able to trace the dependency to the exact code, find the rationale, and explain that the old result does not support the new revision. Include a matching control PR in which the boundary is preserved, and a case where runtime behavior remains unknown. A useful interface also avoids creating false architecture violations.

**Separate the effects of evidence and presentation in the test.** Use comparable PRs and vary the order of conditions where practical. An independent maintainer should establish the expected decision, supporting facts and known unknowns before the sessions.

1. Start with the team's ordinary GitHub, ADR, and CI workflow, including an architecture tool if it is already used.
2. Provide the same prelinked intent, code and evidence in a linear view.
3. Provide those same records through the proposed canvas and evidence panel.

Observe decision correctness, explanations and cited evidence, false confidence, active time, setup and link upkeep. After the task, ask the reviewer to explain the boundary and predict a different change without the interface. Record repeat use on a second PR. Agree decision criteria before running the comparison. If the ordinary workflow is sufficient, pursue a smaller integration or stop. If the evidence helps but the canvas adds little or slows the task, make the evidence easy to use from the PR and revisit where the canvas belongs.

**Limit the first model to the decision.** Reference one intent record, the affected components, the compared code revisions, and scoped observations with provenance. Preserve links to existing records. Where formal approval cannot be established, label the expectation as proposed or unconfirmed. Discover how often this mapping can be reused before expanding into a universal requirements graph, adding agent dispatch, or handling automatic integration.

**Test adoption as well as utility.** A plausible open-source path is an inspectable, portable review artifact that fits a team's current repository and agent workflow. Ask maintainers who would install it, who would maintain the links, and whether they use it again when nobody guides them. A durable business advantage remains unproven. Repeat use, an identified budget owner, and evidence that the tool improves a costly review decision matter more than install counts for that question.

## 7. Limitations and open questions

| Question or limitation | Effect | How to resolve |
|---|---|---|
| How often is the affected decision both consequential and recoverable? | A niche with rare boundary changes may have insufficient repeat use. Poorly documented repos may need an exploration product first. | Observe recent real reviews with maintainers across more than one repository. Record where intent lived and who knew it. |
| Does a canvas improve review or understanding? | A graph may duplicate a well-structured evidence list. | Run the paired comparison and unaided transfer task. Include an accessible linear view. |
| Can the model be seeded and kept current cheaply? | Manual setup and stale references can erase the value of review assistance. | Time initial setup and repeat use. Include an unmodeled component and a moved file. |
| How much can competitors deliver today on the same PR? | Public documentation establishes substantial overlap. Usability, setup cost and private capabilities remain unknown. | Compare an actual ArchiLens or existing-tool workflow with the same fixture. Trial commercial alternatives only when needed and authorized. |
| What evidence can establish behavior or deployment? | Source, checks, merge and persistent runtime state can disagree. | Record the predicate, issuer, environment and revision for each claim. Keep unavailable observations explicit. |
| Is review before merge sufficient, or is prevention before code essential? | The answer changes the first release from a review tool to an intent-authoring workflow. | Ask the decision owner during requirements discovery. Validate with a concrete example of expensive rework. |
